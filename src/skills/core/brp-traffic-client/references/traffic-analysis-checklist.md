# Traffic Analysis Checklist

Use when triaging a capture or debugging a failed replay.

## Contents

- Accepted inputs
- Capture quality
- Endpoint inventory
- Header reduction
- Authentication tracing
- Dynamic value tracing
- Validation matrix
- Write operations
- Deliverable checklist

## Accepted inputs

Any combination is workable; do not demand a HAR when a smaller artifact
suffices.

- `.har` exports, including sanitized or partial ones
- CDP / Chrome DevTools Protocol network logs
- Playwright, Puppeteer, Selenium, or browser-agent traces
- mitmproxy, Charles, Proxyman, Fiddler, or Burp captures
- `curl` commands, "Copy as cURL", "Copy as fetch"
- pasted request headers, payloads, and responses
- server or application debug logs
- existing browser automation code
- OpenAPI or GraphQL schemas discovered during inspection

When evidence is missing, name the minimum additional capture needed.

## Capture quality

- Does the capture include response bodies? HAR often does not.
- Was "Preserve log" enabled across navigation?
- Is the target action isolated, or buried in unrelated traffic?
- Are redirects, preflights, bootstrap calls, and service-worker requests
  present?
- Does the capture expose secrets that must be redacted before sharing or
  committing?

## Endpoint inventory

Record per candidate endpoint. Filter analytics, ads, telemetry, fonts, images,
feature flags, and background polling unless they participate in the target
operation.

| Field        | Questions                                                    |
| ------------ | ------------------------------------------------------------ |
| Purpose      | Which user action triggers it?                               |
| Method       | GET, POST, PUT, PATCH, DELETE, RPC, subscription?            |
| URL          | Which segments and query parameters vary?                    |
| Request body | JSON, form, multipart, GraphQL, binary?                      |
| Response     | Shape, content type, status codes, error schema?             |
| Auth         | Cookie, bearer token, CSRF, signature, device proof?         |
| Pagination   | Cursor, offset, page, date range, continuation token?        |
| Stability    | Public and documented, private and stable, private and thin? |
| Side effects | Read-only, idempotent write, destructive write?              |
| Coverage     | Which record classes does it exclude? Which date range?      |
| Filters      | Which are mandatory? Which widen results when omitted?       |

## Header reduction

Usually keep only:

- `Accept`, `Content-Type`
- authorization or session material
- CSRF headers
- required `Origin` / `Referer`
- application-specific version or client headers
- conditional or range headers when needed

Usually remove unless proven necessary: client hints, fetch metadata, copied
`Cache-Control`, priority headers, tracing and request IDs, analytics
identifiers.

## Authentication tracing

- Where does the initial credential originate?
- Which request exchanges or refreshes it, and what is the expiry signal?
- Are cookies host-only, path-scoped, Secure, HttpOnly, or SameSite restricted?
- Is the session bound to IP, user agent, TLS fingerprint, device ID, or browser
  storage?
- Is a CSRF token paired with a cookie?
- Does logout or refresh invalidate previous tokens?

Preference order for the strategy:

1. documented OAuth or API authentication
2. existing project credentials and session management
3. user-supplied session material from env or a secure local store
4. interactive browser login exporting only the required session state
5. a hybrid CDP bridge when tokens or signatures must be generated by the
   application

## Dynamic value tracing

For each nonce, signature, hash, timestamp, or opaque token:

1. Compare multiple captures to see what actually varies.
2. Search prior responses, cookies, local/session storage, IndexedDB, page HTML,
   JS variables.
3. Inspect the request initiator and call stack.
4. Search loaded JavaScript or source maps for the parameter name.
5. Check whether WebAssembly or a service worker participates.
6. Change one input at a time to infer dependencies.
7. Decide: reimplement, call a bootstrap endpoint, or keep a browser/CDP bridge.

## Validation matrix

- one successful request
- one empty result
- one invalid or expired authentication result
- more than one page when pagination exists
- a repeated run from a new process
- a run after fresh session acquisition
- output parity with the UI for a representative sample
- **two different queries back to back on one session**, asserting the second
  does not return the first one's data (see `stateful-and-bulk-clients.md`)
- **a known-absent case**, confirming the client reports "not found" rather than
  the previous result, and that the caller can tell "absent" from "out of this
  source's scope"

For downloads also validate filename and content disposition, MIME type, file
size, interrupted download behavior, and checksum or parseability.

## Write operations

- Identify state-changing endpoints and their duplicate-submission behavior.
- Add a dry-run mode when meaningful, and require an explicit flag for
  destructive actions.
- Do not loop over a batch until one item has succeeded safely.
- Log identifiers and outcomes without leaking secrets.

## Deliverable checklist

- no live credentials committed; `.env.example` holds names, not values
- logs redact cookies, authorization, API keys, signatures, and personal data
- endpoint assumptions and private-endpoint fragility documented
- refresh and recapture procedure documented
- tests cover parsing and at least one mocked protocol flow
